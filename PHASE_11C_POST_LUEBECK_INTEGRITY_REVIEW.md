       /[locale]/moschee/[city]/[slug]/page: /de/moschee/berlin/interkulturelles-zentrum-fuer-dialog-und-bildung-izdb

### 3.2 Root Cause Analysis
- **Nature of the Failure:** Filesystem concurrency race condition in Windows NTFS during parallel static site prerendering.
- **Mechanism:** Next.js default static page export utilizes a multi-threaded worker pool (`worker.js`) scaled to the CPU core count (8–16 workers on modern hardware). When the export starts, multiple workers simultaneously attempt to prerender routes that share a non-existing parent directory (e.g. `/de/moscheen/dortmund`, `/de/moscheen/koeln`, `/de/moscheen/essen`). Each worker calls `fs.promises.mkdir(parentPath, { recursive: true })`. On Windows NTFS, if thread A opens a file handle to create or check the parent directory while thread B attempts to do the same, NTFS returns `ERROR_ACCESS_DENIED`, which Node.js maps to `EPERM: operation not permitted`.
- **Confirmed Evidence:** The application code, database files, and Next.js page components had zero errors; compilation succeeded (`✓ Compiled successfully`), type checking passed, and page data collection passed. The failure was purely an NTFS directory creation collision across concurrent worker threads.

### 3.3 Next.js Supportability of `cpus: 1`
Inspection of `node_modules/next/dist/server/config-shared.d.ts` in Next.js 14.2.35 confirms that `cpus?: number` is an officially typed, built-in option within `ExperimentalConfig`:
```typescript
export interface ExperimentalConfig {
    ...
    cpus?: number;
    memoryBasedWorkersCount?: boolean;
    workerThreads?: boolean;
    ...
}
```
Setting `cpus: 1` restricts the export worker pool to a single worker process, completely eliminating concurrent directory creation races while keeping the page generation sequence deterministic.

### 3.4 Operational & Runtime Impact
- **Runtime Performance:** Zero impact. The production Node.js runtime server (`next start`) does not utilize build-time export workers; it serves prerendered static files or dynamic requests identically.
- **Artifact Output:** The generated HTML, JSON-LD, chunks, and CSS are 100% identical byte-for-byte to a multi-threaded build.
- **Build Duration:** Prerendering 1,768 static pages on a single thread takes ~40–60 seconds, which is acceptable for deterministic release readiness and local validation.
- **Recommendation:** Keep `experimental: { cpus: 1 }` in place for local builds on Windows to prevent intermittent `EPERM` prerender aborts. Do not revert during this audit.
